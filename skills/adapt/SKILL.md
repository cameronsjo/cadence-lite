# Adapt

Make the next attempt better without making every attempt heavier. The failure
this prevents: repeating a demonstrated workflow mistake, or responding to one
incident by adding permanent instructions everywhere.

## Approach

- **Start from evidence.** Identify what happened, what was expected, and what
  supports the proposed cause. Distinguish an isolated incident, a recurring
  pattern, and a constraint the workflow cannot change. Do not invent recurrence
  or treat a preference as a proven failure.
- **Find the smallest sufficient change.** Check whether an existing mechanism
  already addresses the problem. Prefer a regression test or deterministic check
  when it can catch the failure; otherwise consider a local procedure or concise
  instruction. A reusable skill is warranted only when the workflow genuinely
  repeats across tasks. Keep project-specific knowledge in the project.
- **Explain the tradeoff.** Recommend the change, where it belongs, what it would
  prevent, and how to check that it helps without burdening unrelated work. No
  change is a valid conclusion when the evidence is weak, the problem is already
  covered, or the added complexity costs more than it saves.
- **Apply only authorized changes.** A request for lessons or recommendations does
  not authorize editing instructions, policy, memory, or external systems. If
  implementation is requested, stay within that scope, preserve existing safety
  and approval boundaries, and check the result against the observed failure.

Report what was proposed separately from what was changed and verified. If a
behavioral improvement has not been exercised, name the remaining check rather
than calling the problem solved.
